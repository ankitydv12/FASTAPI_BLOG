PATH PARAMETER: VALIDATION AND HANDLING
=======================================

1. URL parameter
---------------
The route `/api/post/{post_id}` contains a path parameter named `post_id`:

	@app.get("/api/post/{post_id}")
	def get_posts(post_id: int):

The type annotation `post_id: int` tells FastAPI to convert the value from the
URL into an integer before calling the function.

Examples:

- `/api/post/1` is valid and passes `1` to the function.
- `/api/post/abc` is invalid because `abc` is not an integer.
- `/api/post/999` has a valid integer, but the post may not exist.

The page route `/posts/{post_id}` uses the same path-parameter idea. It receives
a `Request` object as well because it returns an HTML template.

Conceptually, a path parameter identifies a resource inside the URL. It is
different from a query parameter: `/api/post/1` identifies post 1 as part of
the URL path, while a query parameter would look like `/api/post?post_id=1`.
FastAPI reads the route template, matches the incoming URL, converts the value
according to its type annotation, and only then calls the route function.

2. HttpException
----------------
`HTTPException` is used when the request is understood but cannot be completed.
In this project, it is raised when the requested post does not exist:

	raise HTTPException(
		status_code=status.HTTP_404_NOT_FOUND,
		detail=f"{post_id} does not exist"
	)

Raising the exception stops the route and sends an error response. `detail`
contains the explanation that can be returned to the client.

Conceptually, an exception is an early exit from normal request processing. It
is preferable to returning an error dictionary manually because FastAPI can
carry the intended HTTP status code and route the error to a registered
exception handler. The client receives an error response instead of a normal
successful response.

3. Status code
--------------
A status code describes the result of an HTTP request.

- `404 NOT FOUND`: the path parameter is valid, but no matching post exists.
- `422 UNPROCESSABLE CONTENT`: the path parameter fails FastAPI validation,
  such as when `post_id` is `abc` instead of an integer.

The project uses named constants such as
`status.HTTP_404_NOT_FOUND` and `status.HTTP_422_UNPROCESSABLE_CONTENT` instead
of writing numeric values directly. This makes the code easier to understand.

HTTP status codes are grouped by their first digit: 2xx means success, 4xx
means the client request cannot be fulfilled as sent, and 5xx means a server
failure. A status code is part of the HTTP response metadata; it is separate
from the response body, which may contain JSON or HTML explaining the result.

4. RequestValidationError
-------------------------
FastAPI raises `RequestValidationError` when incoming request data does not
match the type or rules declared by the route. For this project, requesting
`/api/post/not-a-number` causes validation to fail because `post_id` is declared
as an `int`.

This error happens before `get_posts()` runs. It is different from a 404:

- Invalid path value: `RequestValidationError`, status 422.
- Valid path value with no matching post: `HTTPException`, status 404.

`exception.errors()` returns detailed validation information, including the
location of the invalid value, an error message, and the error type.

Validation protects the route from receiving data in an unexpected shape. It
also gives API clients a predictable 422 response instead of allowing a type
conversion error to occur inside the business logic. The handler can expose
the detailed errors to API clients, while a browser page can show a simpler
message.

5. JSONResponse
---------------
`JSONResponse` creates a response with a JSON body and an explicit status code.
The project uses it for API errors:

	return JSONResponse(
		status_code=exception.status_code,
		content={"detail": message},
	)

Values inside `content` must be JSON serializable. Strings, numbers, lists, and
dictionaries are valid JSON values. A Python `set` is not JSON serializable.
For example, `{message}` creates a set, not a one-item dictionary or string,
and causes `TypeError: Object of type set is not JSON serializable`. The project
correctly keeps `message` as a string and places it in `{"detail": message}`.

JSON is a language-independent text format based on objects, arrays, strings,
numbers, booleans, and null. Python values are converted to JSON during
response serialization. Because JSON has no set type, Python sets must be
converted to lists before being placed in a JSON response. The `content`
argument represents the body, while `status_code` represents the HTTP metadata.

6. HttpException (Starlette)
-----------------------------
FastAPI is built on Starlette. The project imports Starlette's exception class
with an alias:

	from starlette.exceptions import HTTPException as StarletteHTTPException

This type is used when registering the general exception handler:

	@app.exception_handler(StarletteHTTPException)

FastAPI's `HTTPException` can therefore be handled by Starlette's common HTTP
exception mechanism. The handler can read `exception.status_code` and
`exception.detail` from the exception object.

Starlette provides the lower-level web framework used by FastAPI for routing,
requests, responses, and exception processing. Registering a handler for the
Starlette HTTP exception type lets this application customize the default
format of errors generated by FastAPI and Starlette. The alias avoids confusing
the Starlette class with FastAPI's similarly named import.

7. validation_Exception_handler
-------------------------------
This function handles request validation errors for the whole application:

	@app.exception_handler(RequestValidationError)
	def validation_Exception_handler(request: Request,
									 exception: RequestValidationError):

For API paths, it returns validation details as JSON:

	JSONResponse(
		status_code=status.HTTP_422_UNPROCESSABLE_CONTENT,
		content={"details": exception.errors()},
	)

For non-API paths, it returns the error page with a general message. The
function checks `request.url.path.startswith("/api")` to choose between the
JSON response and the page response.

An exception handler is application-level error middleware: it receives the
request and the exception, converts the failure into a response, and prevents
the exception from becoming an unformatted server error. Registering it with
`@app.exception_handler(...)` applies the rule to matching errors across all
routes.

8. general_http_exception_handler
---------------------------------
This function handles Starlette HTTP exceptions for the application:

	@app.exception_handler(StarletteHTTPException)
	def general_http_exception_handler(request: Request,
									   exception: StarletteHTTPException):

It first uses the exception detail, or a fallback message when no detail is
provided:

	message = exception.detail or "An error occurred"

For an API URL, it returns JSON containing the error detail and keeps the
original exception status code. For a normal page URL, it returns the error
template and passes the status code and message to that template.

This gives the same backend error a suitable format for both clients:

- API request: JSON response such as `{"detail": "post not found"}`.
- Page request: HTML error response with the matching HTTP status code.

The handler demonstrates content negotiation by request category. API clients
usually need machine-readable JSON, while browser users need a rendered page.
The request path is used here as a simple project rule for deciding which
representation to return. In a larger API, this decision could also use the
request's `Accept` header or separate routers for API and page endpoints.
