
PYDANTIC SCHEMAS AND FASTAPI VALIDATION
=======================================

These notes explain how `schema.py` works with the API endpoints in `main.py`.

1. What is a schema?
--------------------
A schema is a contract for data. It describes:

- which fields are expected;
- the type of each field;
- rules such as minimum and maximum length; and
- the shape of the data returned by an endpoint.

FastAPI uses Pydantic models as schemas. Pydantic reads incoming data, checks it,
converts compatible values when possible, and reports invalid data clearly.


2. The base model: PostBase
---------------------------
`PostBase` inherits from `BaseModel`, so Pydantic validates every instance of it.

	class PostBase(BaseModel):
		title: str = Field(min_length=1, max_length=50)
		author: str = Field(min_length=1, max_length=20)
		content: str = Field(min_length=1)

The fields mean:

- `title` must be a string from 1 to 50 characters;
- `author` must be a string from 1 to 20 characters; and
- `content` must be a string with at least 1 character.

Because these fields have no default values, they are required. An absent field,
an incorrect type, or a value that violates a `Field` rule causes validation to
fail before the endpoint function runs.

Important distinction:

- `str` checks the data type.
- `min_length` and `max_length` check the size of a string.
- `Field(...)` adds constraints and metadata to a field.


3. Request validation with PostCreate
--------------------------------------
`PostCreate` inherits all fields and rules from `PostBase`:

	class PostCreate(PostBase):
		pass

The `pass` means that this model currently adds nothing new. It is still useful
because it gives the incoming-create request its own meaningful name. Later, the
create request could gain rules without changing the shared base model.

In `main.py`:

	@app.post("/api/posts", response_model=PostResponse)
	def create_post(post: PostCreate):

The type annotation `post: PostCreate` tells FastAPI to treat the request body as
JSON and validate it as a `PostCreate` object.

Example valid request:

	{
	  "title": "Learning FastAPI",
	  "author": "A student",
	  "content": "Pydantic checks my request data."
	}

Example invalid requests include:

- a missing `title`;
- an empty `content`;
- a title longer than 50 characters; or
- an author longer than 20 characters.

For invalid request data, FastAPI normally returns HTTP 422 and does not call
`create_post`. This protects the endpoint from operating on data that does not
match its contract.


4. Response validation with PostResponse
----------------------------------------
`PostResponse` also inherits the three post fields, then adds fields required in
an API response:

	class PostResponse(PostBase):
		model_config = ConfigDict(from_attributes=True)
		id: int
		date_posted: str

Therefore, a response must contain:

- `id` as an integer;
- `title` as a string from 1 to 50 characters;
- `author` as a string from 1 to 20 characters;
- non-empty `content`; and
- `date_posted` as a string.

`response_model=PostResponse` tells FastAPI to validate and serialize the value
returned by the endpoint. It also filters the response to the fields declared by
the model. This is useful because internal fields should not accidentally leak
to API consumers.

The create endpoint returns a newly built dictionary containing all required
response fields. The list and single-post endpoints use the same response model:

	@app.get("/api/posts", response_model=list[PostResponse])
	@app.get("/api/post/{post_id}", response_model=PostResponse)

The first route validates every item in the returned list. The second validates
one returned post. If the application returns data that does not satisfy the
response model, FastAPI raises a server-side response validation error. Request
validation protects the application from the client; response validation
protects the client from an incorrectly shaped API response.


5. Request validation versus response validation
------------------------------------------------

Request validation:

- happens before the endpoint function runs;
- uses `post: PostCreate`;
- checks client input; and
- normally produces HTTP 422 for invalid input.

Response validation:

- happens after the endpoint function returns;
- uses `response_model=PostResponse` or `list[PostResponse]`;
- checks the server's output; and
- documents and controls the public response shape.

Simple flow:

	Client JSON -> PostCreate validation -> endpoint function
				-> Python dictionary -> PostResponse validation -> Client JSON


6. Custom validation error handling
-----------------------------------
`main.py` registers:

	@app.exception_handler(RequestValidationError)

When FastAPI rejects request data, `exception.errors()` contains structured
details such as the location of the bad value, the error type, and a message.

For API routes, the handler returns JSON with status 422:

	{"details": exception.errors()}

For browser/template routes, it renders `error.html` instead. This is a good
example of choosing an error format based on the kind of client making the
request.

The other handler, for `StarletteHTTPException`, handles errors such as a missing
post. API clients receive JSON, while normal web pages receive the error template.


7. `from_attributes=True`
-------------------------
`ConfigDict(from_attributes=True)` allows Pydantic to create a response model
from object attributes, not only from dictionaries. This is especially useful
when an application later returns ORM/database objects such as `post.id` and
`post.title`.

The current application returns dictionaries, so the setting is harmless and
keeps the response model ready for database integration.


8. Important observations in this example
------------------------------------------

- `PostCreate` is for input and intentionally has no `id` or `date_posted`.
- `PostResponse` is for output and requires `id` and `date_posted`.
- The create endpoint currently creates `date_posted` itself instead of asking
  the client to provide it. This is usually the safer design because the server
  controls generated metadata.
- In `create_post`, the expression `max(p["id"] for p in posts) + 1 if post else 1`
  checks `post`, which is a request object and is normally truthy. Conceptually,
  an empty-list check should examine `posts`, not `post`, otherwise `max()` would
  fail when the storage list is empty.
- There are two Python functions named `get_posts`. The later definition replaces
  the earlier Python name, even though FastAPI has already registered the routes.
  Different function names would make the code clearer.


9. Mental model
---------------
Think of Pydantic as a gatekeeper and a formatter:

- before the endpoint: it checks whether client data is acceptable;
- after the endpoint: it checks whether server data matches the promised API;
- in both directions: it gives the data a predictable, documented shape.

This separation makes APIs easier to test, safer to change, and easier for other
developers to use.
