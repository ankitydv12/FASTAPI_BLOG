# FastAPI + SQLAlchemy + Pydantic — Revision Notes
(Based on a Blog API/Website project: Users & Posts)

---

## 1. Overall Architecture

A typical FastAPI project splits into 4 files:

| File | Purpose |
|---|---|
| `database.py` | Engine, session factory, `Base` class, `get_db()` dependency |
| `model.py` | SQLAlchemy ORM models (tables) |
| `schema.py` | Pydantic models (request/response validation) |
| `main.py` | Routes (API endpoints + HTML pages), app setup, exception handlers |

**Why separate schema from model?**
- `model.py` = how data is stored in DB (SQLAlchemy)
- `schema.py` = how data looks going in/out of the API (Pydantic)
- Keeps DB internals hidden from API consumers, allows different shapes for create/update/response.

---

## 2. database.py — Engine & Session

```python
engine = create_engine(url, connect_args={"check_same_thread": False})
SessionLocal = sessionmaker(autocommit=False, autoflush=False, bind=engine)
```

- **Engine** = connection to the actual DB file/server.
- **`check_same_thread=False`** — only needed for SQLite (since FastAPI can use multiple threads).
- **`autocommit=False`** — you must call `db.commit()` yourself.
- **`autoflush=False`** — SQLAlchemy won't auto-sync pending changes before every query.

**`Base`** — all models inherit from this; it collects table metadata so `Base.metadata.create_all()` can create tables.

**`get_db()` — the dependency generator pattern:**
```python
def get_db():
    with SessionLocal() as db:
        yield db
```
- `yield` instead of `return` → this is a **generator**, used with FastAPI's `Depends()`.
- Code before `yield` = setup, code after = teardown (cleanup runs even if request fails).
- `with SessionLocal()` ensures the session auto-closes when done.
- **Key concept:** one DB session per request, injected automatically.

## 3. model.py — ORM Models

```python
class User(Base):
    __tablename__ = "users"
    id: Mapped[int] = mapped_column(primary_key=True)
```
- `Mapped[type]` + `mapped_column()` = modern (SQLAlchemy 2.0 style) way to declare columns.
- `nullable=False` = required field. `unique=True` = no duplicates.

**Relationships (1-to-many: one User → many Posts):**
```python
# On User:
posts: Mapped[list["Post"]] = relationship(back_populates="author", cascade="all, delete-orphan")
# On Post:
user_id: Mapped[int] = mapped_column(ForeignKey("users.id"))
author: Mapped["User"] = relationship(back_populates="posts")
```
- `ForeignKey` = actual DB-level link (column).
- `relationship()` = Python-level convenience (lets you do `post.author` or `user.posts`).
- `back_populates` = keeps both sides in sync.
- `cascade="all, delete-orphan"` = deleting a user deletes their posts too.

**Computed/derived attribute (not stored in DB):**
```python
@property
def image_path(self):
    ...
```
- A `@property` lets you add logic-based fields that aren't real columns but can still be read like `user.image_path`.

## 4. schema.py — Pydantic Validation

**Pattern: Base → Create → Update → Response**
```python
class UserBase(BaseModel):        # shared fields
class UserCreate(UserBase):       # what's needed to create
class UserUpdate(UserBase):       # all fields optional (for PATCH)
class UserResponse(UserBase):     # what's sent back (adds id, etc.)
```
- This avoids repeating fields and keeps each schema's purpose clear.
- `Field(min_length=, max_length=)` — validation constraints.
- `EmailStr` — validates proper email format (needs `email-validator` package).
- **`model_config = ConfigDict(from_attributes=True)`** — required so Pydantic can read data from an ORM object (not just dicts). Without this, returning a SQLAlchemy object from an endpoint would fail.

**Optional fields for PATCH/partial update:**
```python
title: str | None = Field(default=None, ...)
```
- `None` default = field is optional; combined with `exclude_unset=True` (see below) to only update what was actually sent.

## 5. main.py — Core FastAPI Concepts

### a) Dependency Injection
```python
def endpoint(db: Annotated[Session, Depends(get_db)]):
```
- `Depends(get_db)` tells FastAPI to call `get_db()` and inject its yielded value.
- `Annotated[Type, Depends(...)]` is the modern syntax (Python 3.9+).

### b) Path operations & multiple routes → same function
```python
@app.get("/", name="home")
@app.get("/posts", name="post")
def home(...):
```
- Stacking decorators = same view function handles multiple URLs.

### c) Query pattern (SQLAlchemy 2.0 style)
```python
result = db.execute(select(model.Post).where(model.Post.id == post_id))
post = result.scalars().first()   # or .all()
```
- `select()` builds the query, `.execute()` runs it, `.scalars()` unwraps ORM objects, `.first()`/`.all()` fetches results.

### d) Standard CRUD flow
- **Create:** build object → `db.add()` → `db.commit()` → `db.refresh()` (refresh pulls back DB-generated values like `id`).
- **Read:** `select()` + filter + `.first()`/`.all()`.
- **Update (PUT = full replace):** fetch → overwrite all fields → commit.
- **Update (PATCH = partial):** fetch → `data.model_dump(exclude_unset=True)` → loop with `setattr()` → commit.
- **Delete:** fetch → `db.delete(obj)` → `db.commit()`.

### e) Validation before creation (uniqueness checks)
Before creating/updating, manually query to check duplicates (username/email) and raise `HTTPException(400, ...)` if found — since DB-level `unique=True` alone would raise a raw DB error, not a clean API error.

### f) `response_model=`
```python
@app.get("/api/posts", response_model=list[PostResponse])
```
- Filters/shapes the output — only fields defined in the schema go out, even if the ORM object has more.
- Also auto-generates OpenAPI docs.

### g) HTTPException & status codes
```python
raise HTTPException(status_code=status.HTTP_404_NOT_FOUND, detail="...")
```
- Standard way to return errors with proper HTTP codes instead of generic 500s.
- Common codes used: 200 (OK), 201 (Created), 204 (No Content – for deletes), 400 (Bad Request), 404 (Not Found), 422 (Unprocessable Entity – validation errors).

### h) Templates (server-rendered HTML pages)
```python
templates = Jinja2Templates(directory="templates")
return templates.TemplateResponse(request, "home.html", {"posts": posts, "title": title})
```
- Used for HTML pages (not pure API), passes data into Jinja templates.
- `StaticFiles` mounts folders for CSS/JS/images (`/static`) and user-uploaded content (`/media`).

### i) Custom exception handlers
```python
@app.exception_handler(StarletteHTTPException)
@app.exception_handler(RequestValidationError)
```
- Lets you customize error responses globally.
- Common trick: check `request.url.path.startswith("/api")` to decide whether to return **JSON** (for API clients) or a **rendered HTML error page** (for browser users) — same error, two formats depending on caller.

## 6. Key Concepts to Remember (Quick Recall List)

- Dependency injection (`Depends`) → decouples DB session creation from route logic.
- Generator + `yield` in `get_db()` → setup/teardown pattern, auto-closes sessions.
- SQLAlchemy 2.0 query style: `select()` → `execute()` → `.scalars()` → `.first()/.all()`.
- Separate **ORM models** (storage) from **Pydantic schemas** (API contract).
- `from_attributes=True` needed to serialize ORM objects via Pydantic.
- Base/Create/Update/Response schema pattern avoids duplication.
- `exclude_unset=True` → enables true partial updates (PATCH).
- Always manually check uniqueness before insert if DB has `unique=True` constraints, to return clean 400 errors.
- `response_model` shapes and validates what actually leaves the API.
- Custom exception handlers let one app serve both JSON (API) and HTML (web pages) errors.
- Relationships (`relationship`, `back_populates`, `cascade`) link tables at the Python level; `ForeignKey` links them at the DB level.

## 7. Things to Double-Check / Common Bugs (from this code, for learning)

- In `update_user`, comparing `update_data.email != update_data.email` will always be `False` — should compare against `user.email`.
- In `get_user_post`, the initial query filters `model.User` but compares `model.Post.user_id` — mismatched model/condition. Should filter `model.User.id == user_id`.
- Returning `HTTPException(...)` instead of `raise HTTPException(...)` won't actually stop execution or return an error response — must always `raise`.
- In `patch_post`, `Patch_post.model_dump(...)` is called on the class instead of the instance `patch_data.model_dump(...)`.

*(Good to review these later — they're common mistakes to watch out for while practicing CRUD APIs.)*
