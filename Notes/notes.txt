# FastAPI Blog: Templates and Static Files

## 1. Project Overview

This project is a small FastAPI blog application. It demonstrates how a Python backend can:

- Define web routes with FastAPI.
- Render HTML pages on the server with Jinja2.
- Pass Python data into an HTML template.
- Reuse a common HTML layout with template inheritance.
- Serve CSS, JavaScript, images, icons, and a web manifest as static files.
- Generate URLs safely with `url_for`.
- Return structured data from an API endpoint.

The main request flow is:

```text
Browser request
    -> FastAPI route
    -> Python data is prepared
    -> Jinja2 renders an HTML template
    -> Browser receives complete HTML
    -> Browser loads CSS, JavaScript, images, and icons
```

## 2. FastAPI Application Setup

In `main.py`, the application is created with:

```python
app = FastAPI()
```

`FastAPI()` creates the application object. Routes are registered on this object with decorators such as `@app.get(...)`.

The project imports:

```python
from fastapi import FastAPI, Request
from fastapi.templating import Jinja2Templates
from fastapi.staticfiles import StaticFiles
```

### Important terms

- **FastAPI**: The web framework that receives HTTP requests and sends responses.
- **Request**: The current browser request. It is required when rendering a Jinja template response.
- **Jinja2Templates**: FastAPI's integration point for loading and rendering Jinja2 HTML templates.
- **StaticFiles**: A Starlette/FastAPI utility for serving files that do not need server-side rendering.

## 3. Configuring Jinja2

```python
templates = Jinja2Templates(directory="templates")
```

This creates a template environment that looks for HTML files in the project's `templates` directory.

The directory is relative to the process's current working directory. Therefore, the application should normally be started from the project root, for example:

```text
fastapi dev main.py
```

or with Uvicorn:

```text
uvicorn main:app --reload
```

## 4. Serving Static Files

```python
app.mount(
    "/static",
    StaticFiles(directory="static"),
    name="static",
)
```

This mounts the local `static` directory at the URL prefix `/static`.

The mapping works like this:

| Local file | Browser URL |
| --- | --- |
| `static/css/main.css` | `/static/css/main.css` |
| `static/profile_pics/default.jpg` | `/static/profile_pics/default.jpg` |
| `static/icons/favicon.ico` | `/static/icons/favicon.ico` |
| `static/site.webmanifest` | `/static/site.webmanifest` |

The `name="static"` value gives this mounted route a name. That name is later used by Jinja's `url_for` function.

Static files are different from templates:

- A **template** is processed by Jinja and may contain dynamic values.
- A **static file** is sent to the browser as it is, without Jinja processing.

The empty `static/js/utils.js` file is also a static asset. The current theme-switching JavaScript is written directly inside `layout.html`, so `utils.js` is not currently used.

## 5. Routes and Template Responses

### Home route

```python
@app.get("/")
@app.get("/home", include_in_schema=False)
def home(request: Request):
    return templates.TemplateResponse(
        request,
        "home.html",
        {"posts": post, "title": title},
    )
```

The two decorators register the same function for two URLs:

- `/`
- `/home`

`include_in_schema=False` hides `/home` from the automatically generated OpenAPI documentation while keeping the route available.

### What `TemplateResponse` does

`templates.TemplateResponse(...)`:

1. Finds `home.html` in the configured `templates` directory.
2. Makes the supplied context variables available to Jinja.
3. Renders the template into ordinary HTML.
4. Returns that HTML as the HTTP response.

The context is a Python dictionary:

```python
{
    "posts": post,
    "title": title,
}
```

The dictionary keys become Jinja variables. For example, the Python key `posts` is used in the template as `posts`.

The request object is passed as the first argument because the template response needs request context, including route URL generation with `url_for`.

### API route

```python
@app.get("/api/posts")
def get_posts():
    return post
```

When a FastAPI route returns a Python list of dictionaries, FastAPI serializes it to JSON automatically. Therefore:

- `/` returns a rendered HTML page.
- `/api/posts` returns the blog posts as JSON.

post: list[dict] = [

This is useful for learning, but the data will be reset whenever the application restarts. A production blog would normally use a database and typed Pydantic models or ORM models.

The variable `title` is also passed to the template:

```python
title = "Abc title "
```

## 7. Jinja2 Template Syntax

Jinja is a server-side templating language. It allows HTML files to contain dynamic values and control flow.

### Output expression: `{{ ... }}`

```jinja
{{ post.author }}
{{ post.title }}
{{ post.content }}
```

Double curly braces output a value. Jinja automatically escapes normal text output, which helps protect against HTML injection when displaying user-controlled content.

### Statements: `{% ... %}`

Statements control the template but do not directly print text.

Conditional example from `layout.html`:

```jinja
{% if title %}
  <title>FastAPI Blog - {{ title }}</title>
{% else %}
  <title>FastAPI Blog</title>
{% endif %}
```

This checks whether `title` has a truthy value.

Loop example from `home.html`:

```jinja
{% for post in posts %}
  <h2>{{ post.title }}</h2>
{% endfor %}
```

This repeats the article markup once for every item in `posts`.

Dictionary values can be accessed with dot notation, such as `post.author`. Jinja resolves this against the dictionary key.

### Comments: `{# ... #}`

Jinja comments are written with `{# comment #}` and are removed during rendering. The project mostly uses normal HTML comments for notes intended for developers reading the generated template source.

## 8. Template Inheritance

`home.html` begins with:

```jinja
{% extends "layout.html" %}
```

This means `layout.html` is the parent template. It contains the shared document structure:

- `<html>`, `<head>`, and `<body>`
- Navigation bar
- Sidebar
- Footer
- Shared stylesheet and script references

The parent defines a content block:

```jinja
{% block content %}
{% endblock content %}
```

The child fills that block:

```jinja
{% block content %}
  {% for post in posts %}
    ...
  {% endfor %}
{% endblock content %}
```

This avoids copying the full page layout into every page. New pages can extend `layout.html` and replace only the content block.

## 9. `url_for` in Jinja

`url_for` generates a URL using a registered route name instead of hard-coding a path.

### URL for the home route

```jinja
href="{{ url_for('home') }}"
```

The function uses the route's endpoint name. In this project, the Python function is named `home`, so the endpoint name is `home` by default. This generates the URL for the home route.

### URL for a static file

```jinja
href="{{ url_for('static', path='css/main.css') }}"
```

Here:

- `static` is the mount name from `app.mount(..., name="static")`.
- `path` is the path inside the static directory.

More examples from `layout.html`:

```jinja
{{ url_for('static', path='icons/favicon.ico') }}
{{ url_for('static', path='icons/icon.svg') }}
{{ url_for('static', path='site.webmanifest') }}
```

Using `url_for` is better than manually writing paths because route or mount prefixes can be changed in one place. It also keeps links tied to route names rather than duplicated URL strings.

In `home.html`, the profile image currently uses a hard-coded path:

```html
src="/static/profile_pics/default.jpg"
```

For consistency, it could also use:

```jinja
src="{{ url_for('static', path='profile_pics/default.jpg') }}"
```

### Jinja: inherit a layout

```jinja
{% extends "layout.html" %}
```

### Jinja: generate a route URL

```jinja
{{ url_for('home') }}
```

### Jinja: generate a static-file URL

```jinja
{{ url_for('static', path='css/main.css') }}
```
